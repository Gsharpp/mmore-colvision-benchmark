# Results

One `BenchmarkRecord` JSON per cell, at `<study>/<model_id>/<axis>/seed_<n>.json`.
Each record carries the mmore commit, the queryset SHA-256 and the corpus
manifest hash, so a number can always be traced back to what produced it.

Headline tables: [`SUMMARY.md`](SUMMARY.md) — generated by
`scripts/summarize_results.py`, never edited by hand. Regenerate it after any
re-scoring.

## Layout

| Path | Study | Cells |
| --- | --- | --- |
| `track_a/` | ViDoRe v2 `biomedical_lectures_eng_v2`, English | 6 models × 1 |
| `track_b/` | Native-language corpora, English queries | 6 models × 5 langs |
| `track_b_vidore/` | ViDoRe multilingual slice, fixed index | 6 models × 3 langs |
| `baseline_text/` | Dense text baseline, `BAAI/bge-m3` | A + 5 langs |
| `mmore_text/` | mmore's own hybrid text path (dense + SPLADE) | A + 5 langs |
| `_superseded/` | Kept for provenance, **not** to be reported | — |

Track A's queries are ViDoRe's own human-validated, vision-grounded ones with
graded multi-page qrels. Track B's are generated from **page text**, which
favours text retrievers — the standing limitation of that study.

## What `_superseded/` holds

- `track_b_pre_pagefix/` — Track B records produced before commit `353c076`.
  Query generation numbered pages from 0 while mmore emits `page_num + 1`, so
  ColVision runs were scored against the page *before* the relevant one and a
  perfect run scored 0. The text baselines were self-consistent and therefore
  correct, which made text look 2–4× better than ColVision. Re-scored from the
  stored ranked lists — no model was re-run, since the ranking never depended on
  the id convention.
- `track_a_pmc_tiny/` — the abandoned PMC-OA Track A design (palier `tiny`),
  replaced by the ViDoRe corpus.

## Known caveats before quoting these numbers

- **Single seed.** `seeds: [0]` throughout. The bootstrap CIs that
  `results.aggregate.per_cell_ci` produces group by `(model, palier)` and so
  collapse to zero width — they are not confidence intervals and must not be
  reported as such. Per-query scores are not persisted, so no paired
  significance test is currently possible.
- **nDCG uses a linear gain** (`rel / log2(i+1)`), not the exponential
  `(2^rel − 1)` gain of `pytrec_eval` / the ViDoRe leaderboard. Identical on
  binary relevance, divergent on ViDoRe's graded qrels — so the Track A and
  Track B ViDoRe figures are not directly comparable to published ViDoRe scores.
- **MAP and Recall@10 are capped by `top_k=10`.** A query with 20 relevant pages
  scores AP = 0.5 on a perfect run. Report these as MAP@10 / Recall@10.
- **Latency, VRAM and DB size are `null`** in every record:
  `evaluation/performance_metrics.py` is never called. The only timing available
  is `retrieve_duration_total_s / n_queries`. `throughput_pages_per_s` divides by
  the page count *declared in the YAML*, and `process.yaml` sets
  `skip_already_processed: true`, so it inflates on any re-run.
- **No generation metrics.** RAGAS is wired but never executed; `generation` is
  at its default values everywhere.
